TL;DR

Every new attention variant loses PyTorch's fast kernel. GraphSynth writes a replacement. A language model produces the Triton code, a separate stage checks it against PyTorch, and a third stage times it on a GPU. The model cannot call the checker or the timer.

It produced a correct kernel for all ten variants we tested. We then ran the same kernels on a second GPU. The reported speedup went from 10.82× to 32.02×, and the kernels had not changed.

The problem

The gap

Attention scores every pair of tokens, turns the scores into weights, then blends. PyTorch ships one hand-written kernel that does all three at once. It is about 10× faster than doing them separately, because it never writes the full S×S score matrix to memory.

Change any step and that kernel no longer applies. Add a distance penalty to the scores (ALiBi), restrict each token to a window, cap the logits, or use sigmoid instead of softmax. All of these appear in production models today. All of them fall back to the slow path, which writes 0.5 GB of scores per pass.

PyTorch's flex_attention covers the first group, because a bias or a mask can be inserted into a tuned template. It cannot cover the second group. Replacing softmax changes the algorithm, not the scores. Those operators have no fast kernel anywhere.

Method

How it works

Five stages. A program runs four of them. A language model runs one.

  1. Decide whether to optimise — profile_op

    Place the operator on the GPU's roofline. Admit it if memory traffic limits it, or if PyTorch has no fused kernel for it. The second test does the work here: all ten variants look compute-bound, so a roofline test alone would skip every one of them.

  2. Write the kernel — synthesize_kernel

    The model gets the operator in words: shape, dtype, what it should compute. It returns Triton code. On a retry it is told the last attempt failed and where to find the reason. This is the only stage a model runs.

  3. Check it — verify_kernel

    Compare the output to PyTorch at two input scales, using relative error. These outputs are around 0.1 in magnitude, so an absolute tolerance would accept 20% error. Anything producing NaN or Inf is rejected and never timed.

  4. Time it — benchmark_kernel

    CUDA events around a loop long enough to average out dispatch noise, median of three. It also reports achieved bandwidth as a fraction of peak. Above 100% is impossible, so that reading invalidates the timer.

  5. Store everything — SQLiteNode

    Every attempt is saved with its error, passed or failed. The model reads the failures when it retries.

Isolation

What the model can reach

If a model can call the thing that grades it, it will optimise the grader. CHIA has already recorded an agent faking a memory-traffic win that way. So the grader is not callable.

Reachable

  • gs_workbench — read, write, smoke_compile
  • gs_attempts — read-only history

Not reachable

  • verify_kernel
  • benchmark_kernel

Neither reachable tool reports correctness or speed. smoke_compile answers one question: does this build. Its docstring says so in the text the model receives.

Result 02

The same kernels on a second GPU

We ran the loop again on an NVIDIA L40S. The geometric mean went from 10.82× to 32.02×. The kernels were identical.

A speedup is a ratio, and only one side of it is ours. The L40S has 864 GB/s of memory bandwidth; the A100 has 1555. The eager baseline is limited by bandwidth, so it slowed down. The synthesized kernels never write the score matrix, so they did not.

If the baseline's runtime is memory traffic alone, it should slow by 1555/864 = 1.800×. Across all ten operators it slowed by 1.795×. A prediction that could have failed, and did not

Field notes

What the first real run exposed

The measurement stages had never run on a GPU before this evaluation. Three defects appeared in the first three runs. A replay skips the node bodies, so a replay could not have found any of them.

The checker was right and our reference was wrong

The checker rejected a kernel that was correct. Our reference zeroed masked scores before applying sigmoid, and σ(0) = 0.5, so every masked position added half its value vector to the answer we were comparing against.

We found it by reporting ‖K‖/‖R‖ and cosine similarity separately. Both came out at 0.707, and 0.707² = 0.5, which means the output summed over half the terms. Fixing the reference took the error from 1.01 to 4.3×10⁻³.

Then the fix moved the baseline

Masking after the nonlinearity also moved the mask from the bf16 score tensor to the fp32 one, 512 MB against 1 GB. That added about 2 GB of memory traffic per call and raised the eager baseline for two operators by 22%. Two runs looked like a clock transient. A third run, from a clean clone, ruled that out.

Scope

Limitations

These kernels were written for the A100 and re-checked on Ada. The classification, checking and timing stages port across hardware. A kernel written for one device is not tuned for another, and per-head temp is the case where that shows. Two devices is not a trend: the bandwidth prediction held on one pair of GPUs, in one direction, at one shape. One A100 baseline used a profiler-based timer rather than the CUDA-event loop used for the other nine.

Reproduce it

The replay needs no GPU, no API key and no credentials, and finishes in about a minute. The graph, the Ray scheduling, the MCP tool servers and the attempts database all execute for real. Only the node bodies are replayed. 

git clone https://github.com/JoshiP-commits/CHIA_HACKATHON.git
cd CHIA_HACKATHON
pip install -r requirements.txt          # Python 3.10-3.12
