The problem

Standard attention has a hand-tuned fused kernel. Change one thing — add a position bias, mask a sliding window, replace softmax with sigmoid — and that kernel no longer applies. The fallback writes the full S×S score matrix to DRAM and reads it back, which costs roughly 10×. PyTorch's flex_attention recovers the cases expressible as a score modification plus a block mask; it cannot express a replacement for the normalization at all.

The loop

Four stages, persisted by a fifth. Exactly one of them is agentic.

  1. Stage 1 profile_op Classifies the operator against the device roofline. Admitted if memory-bound or not expressible in the fused catalog.
  2. Stage 2 · agentic synthesize_kernel A model reads the operator description in words and writes a Triton kernel, using only the two tools below.
  3. Stage 3 verify_kernel Compares against the PyTorch reference at two input scales. Failure returns a diagnostic and retries.
  4. Stage 4 benchmark_kernel CUDA-event loop timer, plus a bandwidth-utilization check that falsifies the timing method rather than reporting a bad number.

What the model can and cannot reach

This is the part that matters. The correctness gate and the hardware timer are never registered as tools, so the thing deciding whether the model succeeded is not inside the model's search space.

Reachable — the agent's entire surface

  • gs_workbench — read, write, smoke_compile
  • gs_attempts — read-only history

Not reachable — never registered as a tool

  • verify_kernel
  • benchmark_kernel

Neither reachable tool reports correctness or latency. smoke_compile answers one question — does this build — and its docstring says so in the text the model actually receives.

Results on the A100

Ten attention variants, bf16, B=2, H=32, S=2048, D=128. Every kernel below passed the correctness gate before it was timed.

The same kernels on a second GPU

Re-running on an NVIDIA L40S (Ada, sm89) took the geometric mean from 10.82× to 32.02×. Nothing improved. The L40S has 864 GB/s of DRAM bandwidth against the A100's 1555 GB/s. The eager baseline is bandwidth-bound, so it got slower; the synthesized kernels never materialize the score matrix, so they did not.

That gives a prediction worth testing: if the baseline's runtime is memory traffic and nothing else, it should slow by exactly 1555/864 = 1.800×. Measured across all ten operators: 1.795×.

Read honestly: flex_attention is 1.82× faster than GraphSynth on the eight operators it can express. The claim here is coverage and automation — ten of ten, from an operator description in words, with no hand-written pattern or block mask — not peak performance.

What running on real hardware exposed

The measurement stages had never executed on a GPU before this evaluation. Three defects surfaced in the first three runs, none of which a replay could have caught, because a replay bypasses the node bodies. The most useful one:

The gate rejected a kernel that was correct. Our reference zeroed masked scores before applying sigmoid, and σ(0) = 0.5, so every causally masked position was contributing half its value vector to the “correct” answer. The kernel, which skips masked positions properly, was right. Localizing it took one observation: reporting ‖K‖/‖R‖ and cosine similarity separately gave 0.707 for both, and 0.707² = 0.5 identified an output summing over exactly half the terms.

Reproduce it

The replay needs no GPU, no API key and no credentials, and finishes in about a minute. The graph, the Ray scheduling, the MCP tool servers and the attempts database all execute for real; only the node bodies are replayed. 

git clone https://github.com/JoshiP-commits/CHIA_HACKATHON.git
cd CHIA_HACKATHON
pip install -r requirements.txt          # Python 3.10-3.12
python -m chia_loop.loop --bypass chia_loop/configs/bypass_replay.yaml
