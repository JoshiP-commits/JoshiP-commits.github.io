TL;DR. Researchers keep inventing attention variants, and every one of them loses PyTorch's fast kernel. GraphSynth is a loop that has a language model write a replacement kernel, checks it is numerically correct, and times it on real hardware — with the checker and the timer placed where the model cannot reach them.

It produced a verified kernel for all ten variants we tried. Then we ran the same kernels on a second GPU and the headline speedup nearly tripled without a single kernel changing, which is the part of this work worth remembering.

The gap

Attention does three things: score every pair of tokens, normalise the scores into weights, then blend. NVIDIA and PyTorch ship one hand-tuned kernel that fuses all three, and it is roughly 10× faster than doing them separately, because it never writes the full S×S score matrix out to DRAM.

Change any step and that kernel stops applying. Add a distance penalty to the scores (ALiBi), restrict each token to a window, cap the logits, or replace softmax with sigmoid — all of these are in production models today, and all of them fall back to the slow path that materialises 0.5 GB of scores per pass.

PyTorch's flex_attention rescues the first kind: a bias or a mask can be slotted into a tuned template. It cannot rescue the second kind at all, because replacing the normalisation is a different algorithm, not a tweak to the scores. Those operators have no fast path anywhere.

How GraphSynth works

Five stages. A program runs four of them and decides what happens next; a language model drives exactly one.

  1. Decide whether it is worth optimising — profile_op

    Place the operator on the GPU's roofline. Admit it if it is limited by memory traffic, or if PyTorch has no fused kernel for it. The second clause does the real work: all ten variants here look compute-bound on paper, so a roofline test alone would have skipped every one of them.

  2. Write the kernel — synthesize_kernel

    The model is given the operator in words — shape, dtype, what it should compute — and returns Triton code. On a retry it is told the previous attempt failed and to look up why in the attempts database.

  3. Check that it is correct — verify_kernel

    Compare the output against the PyTorch reference at two different input scales, with a relative error bound. These outputs have magnitude around 0.1, so a fixed absolute tolerance would quietly admit 20% error. Anything producing NaN or Inf is rejected and never timed.

  4. Measure it — benchmark_kernel

    CUDA events around a loop long enough to average out dispatch noise, median of three. It also computes achieved bandwidth as a fraction of peak: above 100% is physically impossible, so that result falsifies the timer rather than being published as a speedup.

  5. Remember everything — SQLiteNode

    Every attempt is persisted, passed or failed, with its error. The failures are what the model reads back when it retries.

Why the model cannot see its own score

This is the design decision the paper is built on. If a model can call the thing that grades it, the grader becomes part of what it optimises — and CHIA has already reported an agent gaming an assertion to fake a memory-traffic win. So the grader is not callable.

What the model can reach

  • gs_workbench — read, write, smoke_compile
  • gs_attempts — read-only history

What it cannot — never registered as a tool

  • verify_kernel
  • benchmark_kernel

Neither reachable tool reports correctness or speed. smoke_compile answers one question — does this build — and its docstring says so in the text the model actually receives. There is no score in it to climb.

Result: ten variants on an A100

bf16, B=2, H=32, S=2048, D=128. Every kernel below passed the correctness gate before it was timed.

Result: the same kernels on a second GPU

We re-ran the loop on an NVIDIA L40S (Ada, sm89). The geometric mean went from 10.82× to 32.02×. Nothing improved.

A speedup is a ratio of two numbers, and only one of them is yours. The L40S has 864 GB/s of memory bandwidth against the A100's 1555 GB/s. The eager baseline is bandwidth-bound, so it got much slower; the synthesized kernels never materialise the score matrix, so they did not. The denominator held and the numerator grew.

That gives a prediction that could fail: if the baseline's runtime really is memory traffic and nothing else, it should slow by exactly 1555/864 = 1.800×. Measured across all ten operators: 1.795×.

The honest reading: flex_attention is 1.82× faster than GraphSynth on the eight operators it can express. Where a tuned template covers the operator, the template wins. What GraphSynth offers is coverage and automation — ten of ten, from a description in words, with no hand-written pattern or block mask — not peak performance.

What running on real hardware exposed

The measurement stages had never executed on a GPU before this evaluation. Three defects surfaced in the first three runs, and they share a property: a replay bypasses the node bodies, so no amount of replaying could have caught any of them.

The gate was right and our reference was wrong

The gate rejected a kernel that turned out to be correct. Our reference zeroed masked scores before applying sigmoid — and σ(0) = 0.5, so every causally masked position was contributing half its value vector to the “correct” answer.

Finding it took one observation. Reporting ‖K‖/‖R‖ and cosine similarity separately gave 0.707 for both, and 0.707² = 0.5 says the output is a sub-sum over exactly half the terms — the masked half. Correcting the reference took the operator from a relative error of 1.01 to 4.3×10⁻³.

And the fix moved the thing it was measured against

Masking after the nonlinearity also moved the mask from the bf16 score tensor to the fp32 one — 512 MB against 1 GB — adding about 2 GB of DRAM traffic per call and inflating the eager baseline of two operators by roughly 22%. Two runs made it look like a clock transient; a third, from a clean clone, ruled that out. This is the failure mode to expect from this kind of work: not a wrong kernel, but a correct fix that silently moved the measurement.

What this does not show

These are A100-authored kernels re-verified on Ada. The evaluation shows the classification, verification and measurement stages port across hardware; it does not show that a kernel written for one device is tuned for another, and per-head temp is the case where it is not. Two devices is not a trend — the bandwidth prediction held on one pair of GPUs, in one direction, at one shape. And one A100 baseline came from a profiler-based timer rather than the CUDA-event loop used for the other nine; its ratio is in line, but it is not strictly the same measurement.

Reproduce it

The replay needs no GPU, no API key and no credentials, and finishes in about a minute. The graph, the Ray scheduling, the MCP tool servers and the attempts database all execute for real — only the node bodies are replayed. 

git clone https://github.com/JoshiP-commits/CHIA_HACKATHON.git
cd CHIA_HACKATHON
pip install -r requirements.txt          # Python 3.10-3.12
python -m chia_loop.loop --bypass chia_loop/configs/bypass_replay.yaml
